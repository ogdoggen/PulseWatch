## 1. Идея и цель

PulseWatch — сервис мониторинга HTTP API. Владелец добавляет разрешённый endpoint, выбирает интервал и ожидаемый HTTP-код. Сервис выполняет проверки в фоне, сохраняет результаты, фиксирует сбои и сообщает о падении и восстановлении в Telegram.

Пример: у своего API есть `/health`. PulseWatch проверяет его раз в минуту. После двух последовательных неудачных проверок открывает инцидент. Следующая успешная проверка закрывает инцидент. История показывает HTTP-коды, ошибки соединения и время ответа.

Практическая цель: получить работающий инструмент для собственных API и учебных сервисов. Карьерная цель: дополнить ApplyFlow опытом очередей, фоновой обработки, периодических задач, интеграций и восстановления после сбоев. Учебная цель: научиться самостоятельно объяснять и менять основные механизмы проекта.

Работоспособность демонстрируем на контролируемом сервисе `demo-target`, который умеет отвечать 200, 500 и с задержкой. Для демонстрации внешнее размещение ApplyFlow не требуется.

Совпадение FastAPI, PostgreSQL, SQLAlchemy и Docker Compose намеренное: освоенная основа освобождает время для новых задач.

## 3. Масштаб первой версии

- Один владелец сервиса; доступ к API через ключ из переменной окружения. Без новой системы регистрации и личных кабинетов.
- До 20 активных мониторов в демонстрационной конфигурации.
- HTTP GET; ожидаемый код ответа; интервалы 60, 300 и 900 секунд.
- Предельное время одной сетевой проверки — 5 секунд. Точные сетевые и worker-таймауты согласуем при реализации.
- Проверяемые домены задаёт владелец в конфигурации. Редиректы отключены. Собственный `demo-target` разрешён отдельно в локальном demo-профиле.
- История результатов — 7 суток; инциденты сохраняются отдельно.
- Один Telegram-чат владельца; один канал уведомлений.
- Один репозиторий и общий пакет бизнес-логики; API, worker и beat запускают разные процессы из одного проекта.
- Запуск приложения и тестов через Docker Compose.
- Основная демонстрация через Swagger и сценарий demo. Небольшая HTML-страница — дополнение после готовности backend, максимум 2–3 часа.

Это инструмент для доверенных адресов владельца. Открытая регистрация и приём произвольных URL потребовали бы отдельной работы над сетевыми ограничениями; такая эксплуатация не входит в v1.

## 4. Функциональные требования

| Функция | Поведение v1 | Как проверить |
| --- | --- | --- |
| Управление мониторами | Создать, посмотреть, изменить, поставить на паузу, удалить | API и проверки валидации |
| Разовая проверка | API создаёт задание и возвращает 202 с идентификатором | Worker сохраняет результат отдельно от HTTP-запроса к API |
| Проверки по расписанию | Beat запускает диспетчер; диспетчер выбирает наступившие проверки | Несколько последовательных результатов без ручного запуска |
| История | Пагинация, фильтр по времени, HTTP-код, длительность, категория ошибки | Успех, HTTP 500 и timeout различимы |
| Инциденты | Две последовательные неудачи открывают один инцидент; успех закрывает его | Продолжение сбоя не создаёт новые инциденты |
| Уведомления | Сообщения о начале сбоя и восстановлении; ограниченные повторы доставки | Ошибка отправки не мешает сохранять результаты проверок |
| Статистика | Доля успешных завершённых проверок и среднее/p95 времени ответа за 1 или 24 часа | Формулы и набор учитываемых результатов описаны и проверены |
| Очистка истории | Периодическое удаление старых результатов | Инциденты остаются, выборки не включают удалённую историю |
| Диагностика | Health endpoints и логи с ID монитора/задания | Сбой зависимости можно отличить от сбоя проверяемого сайта |

Доля успешных проверок — измерение по выборке. Она не доказывает непрерывную доступность сайта между проверками. Для пустого периода API возвращает отсутствие данных, а не 100%.

Инциденты описывают наблюдаемый сбой. Начало и конец фактического простоя между измерениями неизвестны. В статистике времени ответа учитываем успешные завершённые HTTP-проверки; ошибки и таймауты считаем отдельно.

## 5. Технологии и ожидаемое понимание

| Технология | Применение | Что Daniil должен уметь объяснить |
| --- | --- | --- |
| Python, FastAPI, Pydantic | Async API, настройки, валидация контрактов | Где выполнение блокируется; что выполняется в запросе и что в worker |
| PostgreSQL | Авторитетное хранилище истории, заданий, инцидентов и доставки | Уникальные ограничения, короткие транзакции, конкурентная запись, EXPLAIN |
| SQLAlchemy 2 async, Alembic | Доступ к БД и миграции | Жизненный цикл сессии, границы транзакции, применение миграции |
| Celery | Очередь выполнения и отдельные workers | Producer, broker, worker, acknowledgment, retry, повторная доставка |
| Celery Beat | Периодический запуск диспетчера и очистки | Чем планировщик отличается от worker; почему интервальные задачи могут пересекаться |
| Redis | Брокер Celery | Что очередь хранит; что происходит при недоступности брокера; почему бизнес-история находится в PostgreSQL |
| HTTPX | Проверки HTTP API и вызовы Telegram | Таймауты, исключения, HTTP-ошибки, закрытие клиента, connection pooling |
| pytest, pytest-asyncio, HTTP mocks | Тесты API, правил инцидентов и сбоев интеграций | Что проверяется с реальной БД/очередью, а где управляемый mock |
| Docker Compose | Повторяемый запуск всех процессов | Сеть контейнеров, переменные окружения, volumes, health checks |
| GitHub Actions, Ruff | Проверки на push/PR | Почему локальный успешный запуск должен воспроизводиться в чистой среде |

API остаётся асинхронным. Обычный Celery worker не начинает автоматически исполнять `async def` как полноценные coroutine-задачи. При реализации выделим явный адаптер между Celery-задачей и async-функцией проверки. Async-клиент, engine и сессии должны принадлежать правильному процессу и event loop; для небольшой первой версии допустимо создавать и закрывать эти ресурсы внутри запуска задачи. Эту границу отдельно проверим тестом нескольких задач подряд.

Для v1 Redis выполняет роль брокера. Кеш статистики с TTL можно добавить после измерения повторяющихся запросов, в пределах 2 дополнительных часов. Кеширование не является критерием готовности.

Версии зависимостей фиксируем в начале реализации после проверки совместимости. Предварительная версия Python — 3.13; это выбор среды проекта, а не заявление о самой новой версии.

## 6. Архитектура и данные

Процессы Compose: `api`, `postgres`, `redis`, `worker`, `beat`. Дополнительный `demo-target` включается demo-профилем. `api`, `worker` и `beat` используют общий исходный код; это разные процессы одного приложения.

Поток работы:

1. API сохраняет настройки монитора в PostgreSQL.
2. Единственный Beat по фиксированному расписанию вызывает диспетчер.
3. Диспетчер выбирает мониторы с наступившим `next_check_at`, сохраняет задания в БД и отправляет их идентификаторы через Redis.
4. Worker получает идентификатор, захватывает право выполнения, проверяет endpoint и сохраняет результат.
5. В короткой транзакции результат обновляет состояние монитора; при переходе состояния создаётся/закрывается инцидент и сохраняется намерение отправить уведомление.
6. Отдельная задача доставки отправляет уведомление и обновляет его статус.
7. API читает историю и вычисляет агрегаты из PostgreSQL.

Предварительные сущности:

| Сущность | Основные данные и ограничения |
| --- | --- |
| Monitor | URL, ожидаемый код, интервал, active, next_check_at, состояние, число последовательных неудач |
| CheckRun | monitor_id, scheduled_at, статус выполнения, started/completed_at, HTTP-код, длительность, категория ошибки, попытка/lease token |
| Incident | monitor_id, opened_at, closed_at; максимум один открытый инцидент на монитор |
| Notification | incident_id, событие down/recovery, pending/sent/failed, attempts, next_attempt_at; уникальность пары incident + event |

Уникальность пары `monitor_id + scheduled_at` предотвращает повторное создание одной плановой проверки. Разовая проверка получает отдельный идентификатор. Индексы на историю выбираем по реальным запросам, начиная с `monitor_id + completed_at`.

API v1: управление `/monitors`; `POST /monitors/{id}/checks`; `GET /checks/{id}`; `GET /monitors/{id}/checks`; `GET /monitors/{id}/stats`; `GET /incidents`; health endpoints. Точный контракт согласуем на первом занятии.

## 7. Надёжность: обязательные инженерные задачи

### 7.1. Повторное выполнение

Доставка задания и выполнение функции не дают гарантии «строго один раз». Проверка имеет постоянный ID; повтор не должен создавать второй результат или второй переход инцидента. Уникальных ограничений недостаточно для всей логики — право выполнения и фиксацию результата согласуем через короткие транзакции.

Не держим DB-транзакцию и row lock открытыми во время HTTP-запроса. Для зависшего исполнения используем ограниченное по времени право выполнения и идентификатор попытки. Поздно завершившаяся старая попытка не должна перезаписать результат новой.

### 7.2. Сбой проверяемого сайта и сбой своей инфраструктуры

HTTP 500, DNS/connect error и timeout целевого сайта — результаты измерения; они учитываются в истории и логике инцидента. Не маскируем их немедленными повторными попытками до первого успеха.

Ошибка доступа к собственной БД, брокеру или API уведомлений — отдельный класс ошибок. Для него задаём ограниченные повторы с возрастающей задержкой и небольшим случайным сдвигом. После исчерпания попыток состояние явно отражается в БД/логах.

### 7.3. Перезапуск и потерянные задания

CheckRun сохраняется до отправки в Redis. Диспетчер повторно подбирает неотправленные/зависшие задания по определённому правилу. После остановки worker очередь и записи БД позволяют продолжить обработку. Просроченные измерения не превращаем в исторические проверки «задним числом» — отмечаем пропуск и запускаем следующую актуальную проверку.

Для одного монитора ограничиваем пересечение плановых проверок. При перегрузке показываем задержку/пропуски, вместо создания бесконечного хвоста задач.

### 7.4. Уведомления

Запись Notification создаётся в той же транзакции, что и изменение инцидента. Повторная обработка события не создаёт новую запись доставки. Постоянные ошибки Telegram, например неверные credentials, не повторяем бесконечно.

При потере ответа от внешнего Telegram API нельзя достоверно определить, было ли сообщение принято. Поэтому абсолютную гарантию отсутствия повторного сообщения не обещаем; документируем это ограничение. Дедупликация бизнес-событий внутри своей БД остаётся обязательной.

## 9. Как разрабатываем вместе

Каждое занятие — одна конкретная задача с проверяемым результатом.

### Обязательный формат объяснений для всех этапов

Правило Daniil от 10 октября 2026 года: перед написанием кода AI объясняет смысл этапа и указывает, что нужно изучить. При введении нового инструмента обязательно объясняет, что он делает, где применяется и какую роль выполняет именно в PulseWatch.

Формат каждого задания:

1. **Смысл:** какую проблему решаем и какой результат получаем.
2. **Подготовка:** какие понятия уже нужны, что повторить или изучить; краткая подготовка относится к времени этапа.
3. **Инструмент:** определение простыми словами, его роль в проекте и минимальная механика использования. Для знакомого инструмента достаточно короткого повторения.
4. **Материал:** проверенная ссылка на официальную документацию, конкретные разделы и ориентир по времени чтения. Краткое объяснение в чате предшествует чтению; ссылка не заменяет объяснение.
5. **Практика:** последовательность действий, распределение работы и пояснение ответственности файлов/функций.
6. **Проверка:** ожидаемое поведение, способы проверки и несколько вопросов на понимание.

Новый инструмент изучаем перед первой задачей, где он нужен. На этапе 0.2 впервые используем pydantic-settings; Celery, Redis и HTTPX разбираем перед их внедрением. Подготовка ограничена знаниями для ближайшего шага, а глубину увеличиваем при появлении соответствующих задач.

Примеры команд из документации адаптируем под запуск через Docker Compose. При появлении ошибки сначала разбираем её смысл и причину, затем исправление. Готовый код от AI сопровождается объяснением ключевых решений.

1. AI объясняет цель, входы/выходы, новое понятие и критерий завершения.
2. Вместе выбираем решение и границы изменений.
3. Daniil пишет согласованную часть; AI может написать соседний модуль, повторяющийся код, конфигурацию или часть тестов.
4. AI проверяет переданный код и объясняет исправления. Команды запускаем через Compose.
5. Daniil объясняет ключевую логику своими словами и делает небольшое изменение без готовой подсказки.
6. Фиксируем законченный шаг отдельным понятным commit и отмечаем следующий.

Роли:

| Работа | Начальная ответственность | Зачем |
| --- | --- | --- |
| Контракт API, схема и поведение инцидентов | Вместе | Решения должны быть понятны владельцу проекта |
| Compose, настройки, каркас CI | AI готовит; Daniil проверяет и запускает | Ускорить повторяющуюся настройку |
| API мониторов, запросы истории | Daniil пишет; AI делает review | Закрепить уже знакомый стек |
| HTTP checker | Вместе, небольшими шагами | Научиться различать сетевые и HTTP-ошибки |
| Celery, scheduler, повторное выполнение | Первый пример вместе; следующий вариант Daniil | Новые механизмы нужно освоить, а не только включить |
| Логика инцидентов | Daniil пишет; AI проверяет сценарии | Основная бизнес-логика должна быть его собственной |
| Тесты сбоев, документация, demo | AI помогает; Daniil воспроизводит результат | Сократить время упаковки и проверить понимание |

Распределение меняем по ситуации. Количество строк, написанных каждым, не является метрикой успеха. Метрика — Daniil может объяснить решение, найти ошибку и самостоятельно изменить поведение.

## 10. Проверки готовности

- Из чистой копии проекта документированная команда Compose запускает все необходимые процессы; порядок миграций воспроизводим.
- Некорректные настройки монитора отвергаются, API требует ключ.
- Проверки успеха, неожиданного HTTP-кода, connect error и timeout сохраняют различные результаты.
- Включение паузы прекращает создание новых плановых проверок; удаление/пауза во время очереди имеет определённое поведение.
- Продолжительный сбой создаёт один открытый инцидент; восстановление закрывает его.
- Повтор одного задания не дублирует результат и переход состояния.
- Остановка worker в ходе задания и последующий запуск приводят к определённому результату восстановления.
- Ошибка доставки уведомления не отменяет результат проверки и изменение инцидента.
- Пропуски измерений и отсутствие данных видны в API; знаменатель статистики описан.
- Основные проверки с настоящим PostgreSQL и отдельный сценарий с настоящими Redis/Celery проходят; eager mode не считается проверкой очереди.
- CI выполняет линтер и значимые тесты. Не ставим искусственную цель «100% coverage».
- Demo показывает последовательность healthy → two failures → incident → recovery.
- README на английском объясняет назначение, запуск, архитектуру, demo, ограничения и тестирование.
- Краткая заметка фиксирует один эксперимент с очередью и один с SQL: набор данных, конфигурация, время/план выполнения, ограничения вывода. Числа в резюме появляются только после измерений.

Основные unit-тесты: переходы состояния, семантика статистики, классификация ошибок. Интеграционные: запись результата и инцидента в одной транзакции, уникальность, конфликт повторов, recovery pending заданий. Сценарный demo проверяет реальные процессы вместе.

## 11. Результат для резюме и собеседования

После готовности проект позволит честно описать:

- Backend сервиса мониторинга HTTP API с периодическими проверками через Celery/Redis.
- Историю результатов и аналитические выборки в PostgreSQL.
- Идемпотентную обработку заданий, ограниченные повторы и восстановление после остановки worker в проверенных сценариях.
- Управление инцидентами и интеграцию уведомлений с Telegram.

Важна воспроизводимость инженерных решений. Проект не заявляется как промышленная замена сервисам мониторинга или как высоконагруженная система без соответствующих измерений.

### 12.1. Задание 0.1 — правила, данные и контракт

Исходный ориентир: 30–45 минут; фактическое время не сообщено. Новых библиотек на этом шаге нет. Результат — `docs/requirements.md`, который описывает договорённости для дальнейшего кода. 10 октября Daniil прислал начальные таблицы и примеры, затем попросил AI завершить 0.1. AI дополнил и оформил документ; файл готов для переноса в репозиторий Daniil. Ниже сохранено задание и основа для разбора, а актуальные требования находятся в готовом документе.

**Смысл.** До реализации нужно определить, что именно приложение считает успехом и сбоем, какие данные хранит и что обещает через API. Это предотвращает неодинаковые правила в checker, API и логике инцидентов.

**Что понять перед выполнением.** Достаточно различать:

- Monitor — настройки того, что и как проверяем.
- CheckRun — одно задание на проверку и его результат.
- Incident — наблюдаемый период сбоя между открытием и восстановлением.
- Контракт API — договорённость о method/path, входных данных, ответе и ошибках.
- Статус выполнения задания и результат измерения — две разные характеристики. Задание может завершиться корректно и сообщить, что сайт вернул 500.

В черновике CheckRun `status` описывает выполнение: pending, running, completed. `is_success` описывает успешность проверки сайта: true, false или отсутствие результата. Например, после полученного HTTP 500 задание completed, а проверка is_success=false. Дополнительные состояния пропусков/восстановления уточним перед очередью.

**Последовательность действий.**

1. Создать каталог проекта `pulsewatch` и каталог `docs` в нём.
2. Создать `docs/requirements.md` с разделами «Назначение», «Правила», «Сущности», «Контракт API», «Примеры поведения».
3. Коротко описать назначение PulseWatch своими словами.
4. Проверить и записать правила ниже, отмечая непонятные места для совместного разбора.
5. Записать черновик Monitor/CheckRun и целевых endpoints.
6. Разобрать примеры последовательностей ответов; сверить их с правилами.

Стартовые правила:

- Проверяем HTTP GET по разрешённому URL, без перехода по редиректам.
- Успех — полученный код совпал с ожидаемым; по умолчанию ожидаем 200.
- Неожиданный HTTP-код, ошибка соединения и timeout целевого endpoint — неудачная проверка.
- Плановые интервалы — 60, 300 или 900 секунд; предел сетевой проверки — 5 секунд.
- Две последовательные неудачные завершённые проверки открывают один инцидент.
- Следующие неудачи продолжают этот инцидент; успешная проверка закрывает его и сбрасывает счётчик неудач.
- Пока монитор на паузе, новые плановые проверки не создаются. Поведение уже поставленных задач уточним до внедрения очереди.
- Ошибка собственного PostgreSQL или доставки уведомления не является измерением недоступности проверяемого сайта.

| Поле | Смысл |

| name | Понятное владельцу название |

| Поле | Смысл |

| --- | --- | --- |
| POST /monitors | name, url, expected_status_code, interval_seconds | 201 и созданный монитор |
| GET /monitors | limit/offset для списка | 200 и список мониторов |
| PATCH /monitors/{id} | Изменяемые поля, включая is_active | 200 и обновлённый монитор |
| POST /monitors/{id}/checks | Идентификатор монитора в URL | 202 и CheckRun с id/status=pending |
| GET /checks/{id} | Идентификатор проверки | 200 и статус/результат CheckRun |
| GET /monitors/{id}/checks | Фильтр времени, limit/offset | 200 и история |

Для create уточняем ограничения: name непустое; URL HTTP/HTTPS из разрешённого списка; interval_seconds из заданного набора; expected_status_code — допустимый окончательный HTTP-код 200–599. У отсутствующего ресурса ожидаем 404, у неправильных входных данных — 422; доступ к бизнес-endpoints требует API-ключ. Конкретные схемы ошибок/заголовок ключа зафиксируем перед реализацией соответствующего API.

Контракт описывает конечное поведение. Очередь и POST разовой проверки реализуются на этапе 2; сейчас они записаны для согласованности модели. GET одного монитора, удаление, статистику и инциденты детализируем перед их реализацией.

Примеры при ожидаемом 200:

- 200 → 500 → 500 → 500 → 200: первый 500 увеличивает счётчик; второй открывает инцидент; третий продолжает его; последний 200 закрывает.
- 500 → 200 → 500: успех сбрасывает счётчик, две последовательные неудачи не накопились, инцидент не открывается.
- Timeout → timeout → 200: инцидент открывается после второго timeout и закрывается после успешного ответа.

### 13.5. 1.3 — API мониторов

**Подготовка, 15–20 минут.** FastAPI: [Dependencies with yield](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/) — A database dependency with yield; [Body Updates](https://fastapi.tiangolo.com/tutorial/body-updates/) — Partial updates with PATCH, exclude_unset.

**Контракт.**
- POST /monitors — 201 и созданный монитор.
- GET /monitors — 200, limit/offset и стабильный порядок.
- PATCH /monitors/{id} — 200; отсутствующие поля сохраняют значения.
- Отсутствующий ресурс — 404; неверные данные — 422.
- Один настроенный API-ключ в X-API-Key для бизнес-endpoint; отсутствующий/неверный ключ — 401. Health остаётся доступен без ключа.

**Валидация.** HTTP/HTTPS URL; точное совпадение нормализованного hostname с настроенным allowlist, demo-target разрешается явно. Пустое имя, недопустимый код или интервал отвергаются. Pydantic URL преобразуется в строку при сохранении в SQLAlchemy. У PATCH различаем пропущенное поле и явно переданный null; обязательные поля нельзя очистить через null.

**Роли.** Daniil пишет схемы и маршруты по знакомой структуре ApplyFlow; AI делает review, помогает с зависимостями и тестовым окружением. Первые тесты проверяют создание/чтение, частичное обновление, ограничения и доступ по ключу. Используем отдельную тестовую PostgreSQL.

### 13.6. 1.4 — HTTPX и demo-target

**Подготовка, 15–25 минут.** HTTPX: [Async Support](https://www.python-httpx.org/async/) — Making Async requests, Opening and closing clients; [Timeouts](https://www.python-httpx.org/advanced/timeouts/); [Exceptions](https://www.python-httpx.org/exceptions/). Перед тестами разобрать [Mock transports](https://www.python-httpx.org/advanced/transports/#mock-transports).

**Практика.**
- Добавить demo-target в Compose с маршрутами /ok, /fail и /slow: 200, 500 и задержка до отправки ответа.
- Написать async checker, который принимает настройки проверки и возвращает результат без доступа к БД.
- Выполнять GET без перехода по редиректам. Успех определяется равенством expected_status_code; не считать каждый 2xx успехом автоматически.
- Ограничить общую сетевую проверку дедлайном 5 секунд; учесть, что таймаут HTTPX для отдельной сетевой операции сам по себе не задаёт такой общий предел.
- Уточнить измерение: response_time_ms — монотонное время до получения заголовков ответа; тело целиком не скачиваем. При отсутствии HTTP-ответа значение null, как записано в требованиях.
- Различать unexpected_status_code, timeout, connection_error. Ошибки своей БД к этим результатам не относятся.
- Управлять жизненным циклом AsyncClient; освобождать сетевые ресурсы и не создавать клиента заново для каждого обращения в цикле.
- Тестировать ожидаемый 200, неожиданный 500, ожидаемый 204, редирект без перехода, timeout и connection_error. Моки делают сетевые сценарии быстрыми и воспроизводимыми; demo-target подтверждает работу реального HTTP.
