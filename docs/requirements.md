# PulseWatch — требования первой версии

Дата: 10 октября 2026 года. Результат шага 0.1.

## Назначение

PulseWatch — сервис мониторинга HTTP API. Владелец задаёт адрес, ожидаемый HTTP-код и интервал. Сервис проверяет адрес в фоне, сохраняет результаты и сообщает в Telegram о начале сбоя и восстановлении.

Практическая цель — следить за собственными API и учебными сервисами. Учебная цель — освоить фоновые задания, расписание, сетевые ошибки и обработку повторов. Проект дополняет ApplyFlow новым опытом для резюме.

Этот документ фиксирует поведение, которое предстоит реализовать. Наличие требований не означает, что функции уже работают.

## Границы первой версии

- Один владелец, доступ к бизнес-API по API-ключу; один Telegram-чат.
- До 20 активных мониторов в демонстрационной конфигурации.
- Проверка HTTP GET по доверенным адресам: разрешённые домены задаются в конфигурации, локальный `demo-target` разрешается отдельно.
- Локальный запуск приложения и тестов через Docker Compose.
- История проверок хранится 7 суток; инциденты сохраняются отдельно.
- Демонстрация через Swagger и контролируемый сервис с ответами 200, 500 и задержкой. Можно также проверять разрешённые реальные API.
- Регистрация пользователей, сложный интерфейс и обязательный деплой не входят в первую версию.

## Правила проверки

1. Выполняем GET по указанному URL. По редиректам не переходим: оцениваем код исходного ответа.
2. Успех — полученный HTTP-код равен `expected_status_code`. По умолчанию ожидаем 200.
3. Неожиданный HTTP-код, таймаут или ошибка соединения — неудачная проверка. Поэтому HTTP 500 при ожидаемом 200 — сбой, а HTTP 204 при ожидаемом 204 — успех.
4. Допустимые интервалы: 60, 300 и 900 секунд. Это интервал планирования; выполнение может начаться позже из-за очереди.
5. Предельное время сетевой проверки — 5 секунд. Настройку общего предела и отдельных сетевых таймаутов определим при реализации checker.
6. Пока результат не получен, `is_success=null`. Отсутствие результата не считаем неудачей сайта.
7. Ошибка собственного PostgreSQL, очереди или доставки Telegram-сообщения не считается результатом проверки целевого API.
8. Результат описывает доступность адреса с точки зрения PulseWatch в момент измерения. Между проверками состояние адреса неизвестно.

## Инциденты

Инцидент — запись о наблюдаемой серии сбоев одного монитора. Он открывается после второй подряд неудачной завершённой проверки и закрывается при следующей успешной проверке.

- Первая неудача увеличивает счётчик до 1; инцидент ещё не открывается.
- Вторая неудача увеличивает счётчик до 2 и открывает один инцидент.
- Последующие неудачи продолжают тот же инцидент.
- Успех сбрасывает счётчик до 0 и закрывает открытый инцидент, если он есть.
- Для монитора одновременно может быть открыт только один инцидент.
- Плановые и ручные проверки используют одинаковые правила оценки и учитываются в последовательности результатов.
- Открытие и закрытие инцидента создают уведомления о сбое и восстановлении. Ошибка отправки не отменяет сохранённый результат или переход состояния инцидента.

Серия определяется отдельно для каждого монитора. Повторная обработка одного задания не должна повторно увеличивать счётчик или создавать новый инцидент. Защиту от повторов и порядок обработки результатов реализуем на этапе фоновых заданий.

## Пауза и ручная проверка

`is_active=true` включает плановые проверки. `is_active=false` ставит монитор на паузу: новые плановые задания для него не создаются. История и настройки сохраняются.

Ручная проверка доступна и на паузе: владелец может проверить адрес, не включая расписание. API создаёт отдельный `CheckRun` и возвращает его идентификатор. Результат выполняется и сохраняется в фоне.

Пауза сама по себе не закрывает инцидент и не считается успешной проверкой. Поведение заданий, поставленных в очередь до паузы, и изменение настроек во время выполнения уточним перед внедрением очереди.

## Сущности

### Monitor

Настройки одного проверяемого адреса.

| Поле | Назначение |
| --- | --- |
| `id` | Идентификатор, создаваемый приложением |
| `name` | Понятное владельцу название |
| `url` | HTTP/HTTPS-адрес проверки из разрешённого списка |
| `expected_status_code` | Ожидаемый окончательный HTTP-код, от 200 до 599; по умолчанию 200 |
| `interval_seconds` | Интервал планирования: 60, 300 или 900 секунд |
| `is_active` | Включены ли плановые проверки; при создании — `true` |

### CheckRun

Одно задание на проверку монитора и его результат. Один Monitor имеет много CheckRun.

| Поле | Назначение |
| --- | --- |
| `id` | Идентификатор задания, создаваемый приложением |
| `monitor_id` | Идентификатор проверяемого монитора |
| `scheduled_at` | Когда проверка должна была начаться; для ручной проверки — момент заказа |
| `completed_at` | Когда результат проверки зафиксирован; до завершения — `null` |
| `status` | Состояние выполнения: `pending`, `running`, `completed` |
| `is_success` | `true` — ожидаемый код; `false` — неудачная проверка; `null` — результата ещё нет |
| `http_status_code` | Полученный HTTP-код; если HTTP-ответа нет — `null` |
| `response_time_ms` | Время получения HTTP-ответа в миллисекундах, включая ответ с неожиданным кодом; если ответа нет — `null` |
| `error_type` | Категория неудачи: `unexpected_status_code`, `timeout`, `connection_error`; при успехе и до результата — `null` |

Временные отметки храним в UTC и передаём с указанием часового пояса. Точные типы идентификаторов и столбцов выберем перед созданием моделей.

`status` и `is_success` отвечают на разные вопросы:

| `status` | `is_success` | Значение |
| --- | --- | --- |
| `pending` | `null` | Задание создано, проверка ещё не началась |
| `running` | `null` | Проверка выполняется, результата ещё нет |
| `completed` | `true` | Проверка завершена, получен ожидаемый код |
| `completed` | `false` | Проверка завершена, зафиксирован неожиданный код или сетевая ошибка |

Например, HTTP 500 при ожидаемом 200 даёт `status=completed`, `is_success=false`, `http_status_code=500`, `error_type=unexpected_status_code`. При таймауте проверка также `completed` и неуспешна, но HTTP-код отсутствует.

Это начальная схема. Модель Incident, служебные поля расписания, повторы и восстановление зависших заданий детализируем на соответствующих этапах. `pending/running/completed` описывают обычный путь проверки; дополнительные состояния собственных сбоев приложения уточним до реализации worker.

## Минимальный контракт API

| Запрос | Входные данные | Назначение | Успешный ответ |
| --- | --- | --- | --- |
| `POST /monitors` | `name`, `url`, `interval_seconds`; `expected_status_code` можно опустить для 200 | Создать активный монитор | 201 и монитор |
| `GET /monitors` | Параметры пагинации `limit`, `offset` | Получить список мониторов | 200 и список |
| `PATCH /monitors/{id}` | Переданные настройки из `name`, `url`, `expected_status_code`, `interval_seconds`, `is_active` | Изменить настройки или поставить на паузу | 200 и монитор |
| `POST /monitors/{id}/checks` | Идентификатор монитора в URL; тело не требуется | Заказать разовую проверку | 202 и идентификатор задания с `status=pending` |
| `GET /checks/{id}` | Идентификатор задания в URL | Узнать состояние и результат | 200 и CheckRun |
| `GET /monitors/{id}/checks` | Идентификатор монитора; `limit`, `offset`, фильтр по времени | Получить историю проверок | 200 и список CheckRun |

Поля `id`, результаты и временные отметки создаёт приложение; клиент не передаёт их при создании монитора. PATCH меняет только переданные поля.

Ответ 202 означает, что задание принято, а результат появится позже. Для завершившейся проверки с `is_success=false` запрос `GET /checks/{id}` всё равно возвращает 200: API успешно выдал запись о неудачной проверке сайта.

Ошибки API:

| Ситуация | Ответ |
| --- | --- |
| Монитор или проверка не найдены | 404 |
| Имя пустое, URL не разрешён, интервал вне набора или ожидаемый код вне диапазона | 422 |
| API-ключ отсутствует или неверен | 401 |

Все бизнес-endpoints требуют API-ключа. Заголовок ключа, значения по умолчанию и пределы пагинации, порядок сортировки, названия временных фильтров и точные JSON-схемы закрепим перед реализацией API. GET одного монитора, удаление, инциденты и статистику добавим в контракт перед соответствующими задачами.

## Примеры поведения

Во всех примерах ожидаемый код — 200. В начале нет открытого инцидента, счётчик неудач равен 0.

### `200 → 500 → 500 → 500 → 200`

| Проверка | Счётчик | Действие |
| --- | --- | --- |
| 200 | 0 | Успех, инцидента нет |
| Первый 500 | 1 | Одиночная неудача |
| Второй 500 | 2 | Открываем инцидент и создаём уведомление о сбое |
| Третий 500 | 3 | Продолжаем тот же инцидент |
| 200 | 0 | Закрываем инцидент и создаём уведомление о восстановлении |

### `500 → 200 → 500`

Инцидент не открывается: успех прерывает серию неудач. Счётчик меняется `1 → 0 → 1`.

### `timeout → timeout → 200`

Первый таймаут увеличивает счётчик до 1. Второй открывает инцидент. Следующий успешный ответ закрывает его и сбрасывает счётчик.
